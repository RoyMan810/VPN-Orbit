# Управление VPS

[Документация](README.md)

## Подготовка VPS

Подготовка и подключение — два разных действия. Администратор настраивает ограниченный SSH-доступ и утверждает цель; владелец регистрирует её в WebUI. Пустая политика не разрешает подключение произвольных серверов. Установленный контроллер связывает политику с хостом и журналом Authority: простая замена файла не добавляет полномочия.

1. Для подготовки VPS используйте Ubuntu 24.04/26.04 или Debian 13 amd64 с OpenSSH и установленным `sudo`. Подойдёт вход как `root` или через администратора с `sudo`. Из доверенной консоли получите отпечаток хоста:

   ```sh
   ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub -E sha256
   ```

2. На машине администратора с Python 3 и клиентом OpenSSH, из доверенного checkout, подставьте IPv4, логин и проверенный отпечаток:

   ```sh
   python3 tools/prepare_vps.py --host 192.0.2.20 --user ubuntu \
     --fingerprint 'SHA256:…' --check
   ```

   `--check` проверяет ОС, архитектуру, зависимости SSH и совпадение свойств существующей служебной учётной записи. Для подготовки выполните команду с каталогом результата:

   ```sh
   python3 tools/prepare_vps.py --host 192.0.2.20 --user ubuntu \
     --fingerprint 'SHA256:…' --output "$HOME/vpn-orbit-managed-vps"
   ```

   Без `--identity ~/.ssh/id_ed25519` OpenSSH интерактивно запрашивает пароль. Для другого порта есть `--port`. Утилита создаёт ограниченную учётную запись наблюдения `vpn-orbit-svc` и проверяет её, но не ставит Docker или зависимости приложений. Каталог результата закрытый: там политика, журнал и приватный ключ. Не отправляйте его в Git или в обращения поддержки. Повторяйте незавершённую подготовку с теми же пользователем, адресом, портом, отпечатком и каталогом; `--cleanup` удаляет только артефакты этой подготовки. Не очищайте используемый SSH-профиль.

   Утилита сохраняет совпадающие служебные файлы на VPS. Отличие содержимого, владельца или режима останавливает установку файла. Удалённый журнал привязан к публичному ключу наблюдения. Очистка проверяет эту привязку и сохранённые отпечатки файлов. Старые журналы без привязки требуют проверки администратором через консоль VPS. Настройки и файлы firewall создаются только при `--firewall`.

   При повторе незавершённого запуска утилита сначала сверяет начатый этап без записи. Подтверждённые действия пропускаются, отсутствующие артефакты устанавливаются после проверки журнала. При конфликте или недоступной сверке подготовка останавливается с записью причины в локальный журнал. Подготовку завершают две независимые проверки: новый вход по ключу наблюдения и новый вход администратора с прежними правами. При недоступном административном входе сохраните ключи и журнал. Восстановите вход через доверенную консоль VPS и повторите проверку той же командой. При `--firewall` утилита также повторно загружает проверенный SSH-профиль для обеих учётных записей.

3. Передайте проверенный `targets.json` при **свежей** [установке контроллера](installation.md): `sudo ./VPN-Orbit/install --targets "$HOME/vpn-orbit-managed-vps/targets.json"`. Для этого вызова регистрация через WebUI включается автоматически. Сохраните Resource ID, Secret Reference и ID созданного владельца. Для нескольких VPS администратор передаёт объединённый защищённый список; корневой формат — `v: 1` и `targets`.

### Импорт ключа наблюдения

На контроллере подставьте `TARGET_ID` (Resource ID), `SECRET_ID` (Secret Reference без `:v1`) и `OWNER_ID` (из вывода создания владельца). Если политика не на первой ревизии, укажите её явно `--policy-revision`. Передавайте файл ключа только по доверенному каналу.

```sh
sudo install -d -m 0700 -o vpn-orbit-broker -g vpn-orbit-broker /run/vpn-orbit/key-import
sudo install -m 0600 -o vpn-orbit-broker -g vpn-orbit-broker \
  "$HOME/vpn-orbit-managed-vps/probe" /run/vpn-orbit/key-import/probe
sudo systemd-run --wait --pipe --collect \
  --property=User=vpn-orbit-broker --property=Group=vpn-orbit-broker \
  --property=UMask=0077 \
  --property=LoadCredentialEncrypted=broker-dek:/etc/vpn-orbit/credentials/broker-dek.cred \
  /opt/vpn-orbit/venv/bin/vpn-orbit-runtime --config /etc/vpn-orbit/runtime.json import-key \
  --key-file /run/vpn-orbit/key-import/probe --target "$TARGET_ID" \
  --secret-id "$SECRET_ID" --owner-id "$OWNER_ID"
```

После успешного импорта удалите временную копию: `sudo rm /run/vpn-orbit/key-import/probe`. Для firewall, перезапуска и приложений нужны отдельные ключи, аккаунты и ссылки в root-политике. Для импорта используется тот же профиль Broker, но своя команда: `import-firewall-key`, `import-restart-key` или `import-application-key`.

## Подготовка через Worker

Для новой VPS укажите в доверенной политике только `host.prepare` и `host.probe`. При установке задайте проверенный ключ хоста и точную версию ключа наблюдения. Импортируйте эту версию в Vault через [импорт ключа наблюдения](#импорт-ключа-наблюдения).

На контроллере выполните команду от root:

```sh
sudo /opt/vpn-orbit/venv/bin/vpn-orbit-runtime --config /etc/vpn-orbit/runtime.json \
  prepare-observation --target "$TARGET_ID" --user ubuntu
```

Пароль вводится в терминале. Для входа по ключу используйте `--admin-key-file` с защищённым файлом root и беспарольным sudo. Broker хранит учётные данные в памяти до начала задания, максимум три минуты. Команда возвращает ID задания. Worker получает один допуск Authority на подготовку и включает ресурс после успешной проверки административного и служебного SSH-входов.

Если задание завершилось с `UNKNOWN_OUTCOME`, запустите `reconcile-preparation` с теми же `--target`, `--user` и дополнительным `--job` с ID задания. Сверка подтверждает полностью выполненную подготовку или фиксирует подтверждённый Authority отказ до записи на VPS. Если Authority зафиксировал неопределённый исход, он блокирует новые удалённые изменения до подтверждения.

Для возобновления частичной подготовки выполните `resume-preparation --target "$TARGET_ID" --user ubuntu --job "$JOB_ID"` на контроллере от root. Broker проверит прежнюю контрольную точку и состояние сервера в режиме чтения. Если последняя удалённая запись подтверждена, а оставшиеся этапы совместимы, команда вернёт ID нового задания. Worker получит новый допуск Authority, повторно сверит подтверждённые этапы и применит недостающие. При повторном вызове с исходным ID команда вернёт уже созданное задание. Если истекли учётные данные новой попытки, подайте подготовку заново. Broker сохранит проверку подтверждённых этапов и остановит задание при расхождении.

Если исход последней записи всё ещё не подтверждён или обнаружено расхождение, проверьте доступ через доверенную консоль VPS. Для ручного завершения используйте `tools/prepare_vps.py` той же версии и исходную пару ключей наблюдения. Поместите `probe` и `probe.pub` в защищённый каталог `--output`, укажите прежние SSH-параметры и отпечаток, затем выполните сверку на контроллере. Удалённый журнал привязан к содержимому `probe.pub`.

## Подключение в WebUI

Для запуска подготовки из WebUI передайте доверенную политику с `host.prepare` и `host.probe` при свежей установке Controller с `--web-enrollment`. Импортируйте версию ключа наблюдения в Vault. В мастере **Подключить VPS** укажите IP, SSH-логин и проверенный отпечаток, введите SSH-данные и нажмите **Подготовить VPS**. Мастер покажет ход настройки и заключительную проверку административного и служебного SSH-входов. После перезагрузки страницы он покажет последнее задание и его подтверждённый прогресс. Для сверки или возобновления на контроллере используйте показанный ID задания.

Для подключения уже подготовленной VPS используйте **Подключить и проверить SSH** или её ID.

1. Как владелец откройте инвентарь и нажмите **Подключить VPS**.
2. Укажите одобренный IP, порт, SSH-логин и отпечаток из консоли. Для разовой проверки вводится пароль или ключ без парольной фразы; они не сохраняются как ключ наблюдения. Можно подключиться по подготовленному ID и проверенному отпечатку.
   Для отдельной проверки нажмите **Проверить готовность VPS**. Controller проверит ОС, архитектуру, конфигурацию OpenSSH и совместимость существующей учётной записи `vpn-orbit-svc`. Проверка выполняется через root или `sudo`. Если для `sudo` нужен пароль, при входе по паролю Controller использует его в рамках той же проверки. При входе по SSH-ключу нужен `sudo` без пароля. Результат относится к текущим параметрам. Эта проверка оставляет VPS вне инвентаря. Для подключения введите учётные данные снова.
3. Дождитесь автоматической SSH-проверки. Если отпечаток изменился, сверьте хост через консоль, а не принимайте новый ключ на основании сетевого ответа.

## Наблюдение и аудит

Кнопка **Запустить SSH-проверку** создаёт задание при наличии `vps:probe`. Свежий успешный результат означает, что ответил ограниченный SSH-helper, а не что все приложения доступны. Последнее успешное наблюдение хранится отдельно и может быть устаревшим. Docker и Nginx обнаруживаются по наличию исполняемых файлов в ожидаемых путях.

Для показа контейнеров Docker укажите до восьми точных ID и их Compose-метки в `/etc/vpn-orbit/docker-discovery.json` на VPS. Нужны каталог, защищённый от записи не-root, и root-owned файл режима `0600`, без hardlink. Пример структуры (замените ID и метки):

```json
{"v":1,"containers":[{"id":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa","project":"fixture","service":"web"}]}
```

После пересоздания контейнера проверьте и обновите его ID. Карточка показывает состояние и опубликованные порты Docker. Раздел **Проекты Compose** группирует сервисы, метки которых удалось подтвердить в разрешённой области. Устаревшие результаты помечаются. Группировка доступна только для просмотра и охватывает заданные ID. Сведения о привязках и внешней доступности проверяются отдельно.

Для обнаружения внешних Compose-проектов без списка ID подготовьте VPS с helper, поддерживающим SSH probe v9. На VPS создайте `/etc/vpn-orbit/compose-discovery.enabled` с содержимым `enabled` и переводом строки. Владелец файла `root`, режим `0600`, родительский каталог доступен на запись только root. Включайте обнаружение, если пользователям Controller с правом чтения этой VPS можно показывать названия её Compose-проектов и сервисов.

Повторите SSH-проверку. Controller покажет контейнеры с метками Compose, включая остановленные. API возвращает имена проекта и сервиса, ID контейнера, локальный ID образа и состояние. При превышении 12 контейнеров карточка сообщает о пределе. Полномочия на операции и состав защищённого `docker-discovery.json` определяются отдельно. Для отключения удалите файл включения и запустите новое наблюдение. Старые helper поддерживают прежний просмотр по заданным ID.

Журнал аудита требует `audit:read` с областью `*`; просмотр истории задания или сохранённого плана дополнительно требует `vps:read` на целевой VPS. В журнале можно сверить целостность Audit/Outbox и выгрузить выбранную категорию текущей страницы в сокращённом JSON.

## Firewall

Включите `tools/prepare_vps.py --firewall` при подготовке утверждённой Ubuntu VPS с nftables. Это добавляет отдельный аккаунт и ключ `vpn-orbit-firewall` и ссылку `firewall_secret_ref` в политику цели. Импортируйте ключ через `import-firewall-key` до запуска операций. Работайте только там, где есть независимый доступ к консоли.

В карточке VPS владелец задаёт типизированные TCP/UDP-правила и входящее разрешение для фактического SSH-порта, сверяет diff, повторно вводит пароль и отправляет подтверждённый план. Произвольные команды и редактирование чужих таблиц не поддерживаются. Исполнитель меняет только таблицу VPN-Orbit, сохраняет прежнее состояние и запускает таймер отката на самой VPS **до** применения. Контроллер подтверждает изменение только после проверки из нового SSH-соединения. Если проверка не пройдёт, таймер не зависит от доступности контроллера. При неопределённом результате используйте [сверку](operations.md#неопределённый-результат).

## Тестовый перезапуск Docker

Это сценарий только для отдельного стенда. На daemon должен быть один явно разрешённый тестовый контейнер без томов и других зависимостей, в сети `none`, с частными namespaces, read-only rootfs, без capabilities, устройств и privileged mode. Полный профиль проверяет [наблюдающий helper](../remote/typed-helper); сценарий приёмки — [стендовый тест](../tests/lab/docker_restart.py).

- Сохраните одинаковый полный ID и Compose-метки в защищённых `docker-discovery.json` и `docker-restart.json` в `/etc/vpn-orbit`. Каталог состояния `/var/lib/vpn-orbit-docker-restart` принадлежит root, режим `0700`.
- Используйте отдельный ключ и аккаунт `vpn-orbit-restart`, root-owned `restart-gateway` и `docker-restart` в `/usr/local/libexec/vpn-orbit/`. На аккаунте нужен `ForceCommand` на gateway, запрет PTY/forwarding/user RC и точное sudo-правило на `docker-restart` **без аргументов** (`""`). В политике цели нужны `host.probe`, `docker.restart` и отдельные `secret_ref` и `restart_secret_ref`; импорт — через `import-restart-key`.
- Получите свежее наблюдение v8, откройте предпросмотр, подтвердите тестовое назначение и запустите проверку готовности. Подтвердите точную ревизию паролем владельца, затем сверяйте статус и хронологию операции. Новое `StartedAt` подтверждает эффект для того же контейнера.
