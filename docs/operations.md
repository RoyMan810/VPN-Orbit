# Обслуживание и диагностика

[Документация](README.md)

## Контроллер и HTTPS

В сборках с `sudo /opt/vpn-orbit/admin diagnose` команда возвращает JSON с временем проверки, версией и состояниями API, Worker, системных служб, Docker, SQLite, Audit/Outbox, Vault, TimeHealth, HTTPS и хранилища копий. `NO_DATA` означает, что компонент не установлен или информация отсутствует; `UNAVAILABLE` — что проверка не смогла связаться с компонентом; `ERROR` — что проверка обнаружила ошибку. `--output /root/orbit-diagnostics.json` дополнительно создаёт новый файл `0600`, не перезаписывая существующий. `--backup-directory` указывает нестандартный каталог копий. Обнаружение архива и его заголовка не заменяет расшифровку и `backup-verify`; диагностика также не расшифровывает Vault и не обращается к управляемым VPS.

Для штатной установки проверьте Compose, прокси и две socket-службы:

```sh
sudo systemctl status vpn-orbit-compose.service vpn-orbit-web.service \
  vpn-orbit-broker.socket vpn-orbit-supervisor.socket
sudo journalctl -n 100 --no-pager -u vpn-orbit-compose.service -u vpn-orbit-web.service \
  -u vpn-orbit-broker.service -u vpn-orbit-supervisor.service
curl --cacert /opt/vpn-orbit-bootstrap/web-ca.pem https://127.0.0.1:18443/healthz
```

Последняя команда — для установки на loopback, с контроллера. Для публичного режима используйте `/healthz` на своём HTTPS-домене и обычную проверку CA. Успех подтверждает ответ API, а не здоровье VPS или доступность операций. При неработающем TLS проверьте домен, режим установки и срок действия сертификата; не заменяйте это игнорированием TLS. При отказе входа учитывайте ограничения на частоту попыток.

| Путь | Назначение |
| --- | --- |
| `/opt/vpn-orbit` | Установленные команды, метаданные установки и `install-state.json` для диагностики. |
| `/opt/vpn-orbit-bootstrap` | Файлы штатного bootstrap, включая WebUI и публичный локальный CA. |
| `/etc/vpn-orbit/runtime.json` и `/etc/vpn-orbit/targets.json` | Защищённая конфигурация и утверждённые SSH-цели. |
| `/var/lib/vpn-orbit` | База контроллера и отдельные журналы Authority/Broker; не редактируйте вручную. |

API слушает loopback. Worker изолирован от сети и не имеет Docker socket, ключей SSH или доступа к Vault; удалённое подключение выполняет Broker. Не изменяйте эти границы ради диагностики. Набор [systemd-профилей](../deploy/systemd) и [пример конфигурации](../deploy/runtime.example.json) описывают соответствующие границы; фактические UID/GID берите из установленного `runtime.json`.

## Резервная копия контроллера

Команды ниже относятся к сборкам из ветки разработки, содержащим `admin backup`; в выпущенной `v1.0.0` их нет. CLI кратковременно блокирует записи, чтобы зафиксировать одну точку для SQLite, очереди и журналов. Затем снимает блокировку и проверяет целостность SQLite, Audit/Outbox, ключи Authority и объекты Vault. Снимок включает незавершённые операции и переносимый ключ Vault внутри шифрования `age`; он **не разрешает** повторять операции и не доказывает, что внешняя инфраструктура не изменилась после снимка.

1. На отдельной защищённой машине создайте обычный ключ `age` командой `age-keygen -o orbit-backup.identity`. Храните две защищённые копии identity отдельно от архивов; на контроллер передайте только открытый recipient (`age-keygen -y orbit-backup.identity`). Потерянный identity невозможно восстановить по recipient.
2. На контроллере создайте отдельный каталог `0700`, принадлежащий root, и сделайте снимок (замените `age1…` на открытый recipient):

   ```sh
   sudo install -d -m 0700 -o root -g root /var/backups/vpn-orbit
   sudo /opt/vpn-orbit/admin backup --directory /var/backups/vpn-orbit --recipient age1…
   ```

3. Перенесите только завершённый `controller-*.age` за пределы исходной VPS. Отдельно сохраните `sha256` из результата команды. На доверенной отдельной машине с тем же CLI, где каталог принадлежит root, а архив и identity имеют режим `0600` (или `0400`), проверьте:

   ```sh
   sudo /opt/vpn-orbit/admin backup-verify \
     --archive /var/backups/vpn-orbit/controller-YYYYMMDDTHHMMSSZ-ID.age \
     --identity /root/orbit-backup.identity --sha256 ЗНАЧЕНИЕ_ИЗ_РЕЗУЛЬТАТА
   ```

   `CREATED` означает, что снимок записан и зашифрован; `VERIFIED` — что отдельная проверка расшифровала и прочитала весь архив, сверив его формат и контрольные суммы, не извлекая файлы. Эта проверка не заменяет пробное восстановление.

Для автоматизации задайте локальный systemd `Type=oneshot`-сервис с `ExecStart=/opt/vpn-orbit/admin backup --directory /var/backups/vpn-orbit --recipient <открытый-ключ>` и таймер с `OnCalendar=daily` и `Persistent=true`. Не храните закрытый identity в сервисе. По умолчанию CLI ничего не удаляет. Необязательный `--retain 14` явно разрешает удалять старые завершённые копии из этого каталога после успешной записи нового снимка. Включайте его только для отдельного хранилища после настройки независимого выноса и периодической проверки копий.

Рабочие снимки SQLite создаются в приватном каталоге tmpfs под `/run/vpn-orbit`: убедитесь, что доступного места хватит для всех баз. При `SIGKILL` временные файлы могут остаться в `/run/vpn-orbit` до перезагрузки, а `.partial` в каталоге копий не считается готовым архивом. Не переносите эти файлы и не публикуйте содержимое tmpfs; если хост использует swap, шифруйте его. Публичные сертификаты и ключи Certbot, Docker-образы и данные Remnawave/Bedolaga в эту копию не входят.

### Восстановление в карантине

Для сборок с `restore-stage` и `restore-apply` сначала установите доверенную сборку той же версии на целевой машине либо используйте совместимую установку на исходной машине. Команды не принимают архив без SHA-256 из доверенной записи о создании. Зашифруйте диск, на котором хранится staging: там окажутся база пользователей, настройки и другие чувствительные файлы. Ключ Vault и ключ Authority перепаковываются средствами systemd, под ключ целевой машины. Для публичного HTTPS заранее отдельно настройте сертификат на целевой машине; конфигурация Docker, сетевого интерфейса и TLS в работающей установке берётся с цели.

```sh
sudo install -d -m 0700 -o root -g root /var/lib/vpn-orbit-recovery
sudo /opt/vpn-orbit/admin restore-stage --archive "$ARCHIVE" --identity "$IDENTITY" --sha256 "$SHA256"
```

`STAGED_READ_ONLY` не изменяет работающую установку. Для применения остановите собственные Compose и host-службы контроллера (включая `vpn-orbit-web.service`, если есть), затем удалите **только остановленные** контейнеры проекта без томов. Используйте Docker socket из установленной конфигурации, если он нестандартный.

```sh
sudo systemctl stop vpn-orbit-compose.service vpn-orbit-broker.service vpn-orbit-supervisor.service \
  vpn-orbit-broker.socket vpn-orbit-supervisor.socket
sudo docker compose --project-name vpn-orbit --file /etc/vpn-orbit/compose.json rm --force
sudo /opt/vpn-orbit/admin restore-apply --sha256 "$SHA256" --confirm-replace
```

После `RESTORED_READ_ONLY` можно запустить socket-службы, Supervisor, Broker, Compose и настроенный HTTPS. Проверьте вход Owner, права, инвентарь и целостность аудита. Имеющиеся сессии больше не действуют. Не начатые задания отменены, а задания с возможным внешним эффектом помечаются `UNKNOWN_OUTCOME`; контроллер **не** выполняет задания или сверку с VPS в этом режиме. Старые данные и конфигурация сохраняются в отдельных приватных каталогах, указанных в результате команды.

Если применение прервалось после начала замены, службы останутся заблокированными. Не удаляйте `/var/lib/vpn-orbit/restore.pending` вручную: повторите `restore-apply` с тем же хешем и `--resume`. Не импортируйте второй архив поверх уже восстановленной установки.

Для активации сначала необратимо отключите доступ исходного контроллера и любых его копий к VPS (например, на сетевом уровне, который не контролируется исходным хостом). Через независимый доступ проверьте состояние каждой цели и завершение внешних операций, включая изменения после снимка. Команда не может доказать, что оператор выполнил эти внешние действия.

Выполните `sudo /opt/vpn-orbit/admin activation-review`. В root-owned JSON режима `0600` задайте поля `binding` (точный вывод команды), `source_fenced: true`, текстовое `evidence` без секретов, `confirmed_at` (Unix UTC в секундах) и `targets`: карта всех ID из `binding.targets`, каждый со значениями `no_outstanding_effects: true` и `postconditions_verified: true` только после проверки. Затем выполните `sudo /opt/vpn-orbit/admin activate --report /root/orbit-activation.json --owner ИМЯ --confirm` и введите пароль Owner. Любой незакрытый инцидент SQLite блокирует активацию; не удаляйте его вручную. При прерывании повторите команду с тем же отчётом: она не возобновляет старые задания, удаляет неподтверждённые черновики и переключает идентификатор Authority. Полное испытание переноса на отдельную VPS требуется отдельно.

### Совместимость данных

`sudo /opt/vpn-orbit/admin schema-check --target-schema 6` проверяет фактические версии пяти баз, режим WAL, основные таблицы и привязку Authority к защищённой политике и хосту. `NOT_REQUIRED` означает, что структура уже совместима; `REQUIRED` выводит точный список известных переходов. Команда ничего не переписывает. Сейчас `restore-stage` транзакционно приводит старый Vault v1 без `secret_lifecycle` к текущему формату: создаёт таблицу истории, сохраняет записи ключей и отмечает переход в `orbit_migration_history` той же транзакцией. При ошибке исходный архив и установленная база не меняются. Не меняйте `PRAGMA user_version` вручную.

### Проверка кандидата на обновление

`sudo /opt/vpn-orbit/admin release-check` сверяет установленную версию с последним стабильным GitHub Release. `UPDATE_AVAILABLE` ещё ничего не говорит о наличии и подлинности комплекта. Перед применением версии администратор должен независимо проверить источник открытого ключа, затем запустить:

```sh
sudo /opt/vpn-orbit/admin update-check --version 1.1.0 --bundle /root/orbit-candidate \
  --trust-key /root/orbit-release.pub
```

`--trust-key` нужен при установке без закреплённого ключа выпуска. Не берите ключ из того же каталога, который проверяете. `update-check` сравнивает подпись, хеши файлов, ожидаемую версию, окружение и контракты данных. Он не скачивает и не запускает комплект, не останавливает сервисы и не применяет обновление.

### Переход с v1.0.0

Для перехода нужна независимо проверенная копия исходников `v1.1.0` и подписанный комплект с той же версией, включая WebUI для установки, сделанной через `./install`. Запускайте переход с локальной консоли через постоянный интерпретатор Python 3.15 (не через `venv` обновляемого приложения). Не применяйте чистую установку поверх существующей:

```sh
sudo /opt/vpn-orbit-bootstrap/python/bin/python3.15 /root/trusted-vpn-orbit/deploy/upgrade.py \
  --bundle /root/vpn-orbit-1.1.0-bundle --trust-key /root/vpn-orbit-release.pub \
  --backup-directory /var/backups/vpn-orbit --recipient "$AGE_RECIPIENT" \
  --identity /run/private-recovery/backup.identity --confirm
```

Используйте закрытый identity только с кратковременно подключённого носителя или приватного tmpfs. Не копируйте его в постоянное хранилище контроллера. CLI закрывает допуск, ждёт выхода начатых операций, останавливает службы, снимает и расшифровывает резервную копию для проверки, затем переключает ПО и проверяет API, WebUI и контейнеры. Решение об открытии допуска фиксируется до возобновления записей.

Если процесс прервался после записи транзакции, запускайте тот же доверенный скрипт с `--resume --confirm` (для фазы `QUIESCENT` повторно нужны параметры копии). Не удаляйте `update.blocked` вручную. При неуспешной проверке запуска CLI пытается вернуть исходную версию, не заменяя базы из архива. До фиксации живых записей можно явно запросить `--rollback --confirm`. Если прежняя схема не читается или запуск не удаётся, оставьте допуск закрытым и используйте проверенную резервную копию. После `COMMITTING` доступен только безопасный повтор команды `--resume`; автоматический откат поверх новых записей запрещён.

## Неопределённый результат

`UNKNOWN_OUTCOME` означает, что действие могло выполниться до потери ответа или перезапуска процесса. Это не обычный отказ. Не запускайте тот же эффект с новым ID, не удаляйте журналы и не пытайтесь разблокировать операцию вручную.

- Если потерян только HTTP-ответ при отправке плана, воспользуйтесь повтором **того же запроса**, если панель его предлагает, либо проверьте уже созданное задание по ID и аудиту. Не подтверждайте новый план взамен.
- Для firewall, приложений и тестового перезапуска используйте сверку в соответствующей хронологии или форме. Сверка читает подтверждения, не выполняет действие заново. При подтверждённом исходе блокировка снимается отдельной записью, но исходное задание сохраняет `UNKNOWN_OUTCOME`.
- При `QUARANTINED` или исчерпании доступных попыток сохраните ID задания и корреляции, код отказа и время. Проверьте утверждённый хост через независимый доступ. Отсутствие доказательства не даёт разрешения на повтор.

## Время и отклонённый план

Изменяющие операции требуют годной выборки TimeHealth от `chrony` или `systemd-timesyncd`. Активным должен быть один источник; при `UNTRUSTED` проверьте его синхронизацию и журнал Supervisor. Временный `HOLDOVER` ограничен и не продлевает разрешение бесконечно. Read-only SSH-проверка не требует допуска на изменение.

```sh
sudo /opt/vpn-orbit/venv/bin/vpn-orbit-runtime \
  --config /etc/vpn-orbit/runtime.json time-health
```

Устаревший план, смена состояния VPS или потеря доверенного времени требуют нового наблюдения и подтверждения новой ревизии после устранения причины. Перезапуск Supervisor не восстанавливает старые допуски. Не переинициализируйте отсутствующий или повреждённый журнал как при свежей установке.

## Проверка сети

Модуль `vpn_orbit.runtime.listener_diagnostics` запускается там, откуда нужно провести проверку, с установленным Python-пакетом VPN-Orbit. Подставьте свои адрес и имена:

```sh
python -m vpn_orbit.runtime.listener_diagnostics --port 443 --check-bind 0.0.0.0
python -m vpn_orbit.runtime.listener_diagnostics --connect 203.0.113.20 \
  --port 443 --tls-name orbit.example.org --https-path /
python -m vpn_orbit.runtime.listener_diagnostics --resolve orbit.example.org \
  --expect-ip 203.0.113.20
```

Первая команда читает локальные TCP-слушатели и не резервирует порт. Вторая проверяет заданный IP из сети запуска, SNI, цепочку и имя TLS, затем выполняет HEAD; путь должен поддерживать HEAD (иначе даже исправный сервис может вернуть `405`). Уберите `--https-path`, чтобы проверить только TCP и TLS. Третья проверяет полный набор адресов, видимых системному резолверу; для IPv6 добавьте отдельный `--expect-ip`. Данные Docker о публикации портов не заменяют эти проверки.

## Аудит и ротация ключей

Для проверки Audit/Outbox используйте действие в журнале WebUI. Локальная проверка читает тот же журнал: укажите путь, UID и GID из `runtime.json` (`database`, `app_uid`, `app_gid`):

```sh
sudo /opt/vpn-orbit/venv/bin/vpn-orbit --database "$DATABASE" \
  --database-owner "$APP_UID" --database-group "$APP_GID" audit-verify
```

Это проверка согласованности цепочки и Outbox, а не защита от администратора, переписавшего всю базу. При диагностике не публикуйте ключи, токены, файлы Vault или необработанную базу.

Ротация или отзыв ключа через `vpn-orbit-runtime rotate-key` / `revoke-key` выполняются с тем же UID и зашифрованным systemd credential, что и [импорт](vps.md#импорт-ключа-наблюдения). Для `--purpose` выберите `host.probe`, `docker.restart`, `firewall.apply` или `apps.lifecycle`. Передайте точную текущую версию `--reference`, `--target` и `--policy-revision`.

Перед ротацией приостановите новые задания для цели и дождитесь окончания текущих. Установите новый открытый ключ на VPS с прежними ограничениями, передайте закрытый ключ в приватный `--key-file`, сохраните новую ссылку из вывода. Не меняйте исходную ссылку в защищённой политике: она задаёт начало цепочки. Проверьте новый доступ до удаления старого открытого ключа. При отзыве удалите открытый ключ и на VPS: локальная блокировка цепочки не отзывает доступ вне контроллера.
